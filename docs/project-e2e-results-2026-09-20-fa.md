این گزارش مربوط به اجرای واقعی روی Windows، Node 22.15.0، npm 10.9.2، Java 21 و Docker Desktop است. مرجع آموزش کار با سیستم: [راهنمای مدیریت میکرو، دسترسی، گزارش و Route](project-management-and-e2e-fa.md).

commit پایه: `624523fd327c2e9072f693a97d4bfe24630fecad`، همراه اصلاحات runner و مستندات همین بررسی. تاریخ محلی ۲۰ سپتامبر است؛ timestampهای UTC بعضی شواهد هنوز ۱۹ سپتامبر را نشان می‌دهند.

[شاهد ماشینی پالایش‌شده: نتایج کامل و بازآزمایی‌های محدود](evidence/project-e2e-2026-09-20.json)

«PASS» فقط برای assertion اجراشده است. آزمون واحد، قرارداد کد، integration روی سرویس واقعی و مرورگر جدا گزارش می‌شوند. عبور تست‌های موجود به معنی پوشش همه ترکیب‌های ممکن فرم‌ها، بار عملیاتی، همه مرورگرها یا تمام سیاست‌های داده نیست.

## چه چیزی در دسترسی واقعاً آزمایش شد؟

تست `PermissionLifecycleIntegrationTest` روی PostgreSQL، Redis و OpenFGA ایزوله اجرا شد؛ این اجرا فقط mock نبود. پوشش آن شامل grant مستقیم، عضویت Directory Group، Access Group، مسیرهای انتساب Role، غیرفعال/فعال کردن نقش، لغو grant، انقضای grant و assignment، قطع و بازیابی OpenFGA، dead-letter، reconciliation و idempotency، هویت canonical، مجوز مستقل یک dashboard و توضیح مسیر دسترسی است.

دو کلاس دیگر، reconciliation واقعی دیتابیس و diagnostics را با migrationهای پروژه بررسی کردند. سناریوهای درخت، Manifest، Action، Registry، proxy و Superset نیز در مجموعه Java و frontend اجرا شدند. UI فرم‌های مدیریتی جدا در مرورگر بررسی شد.

## آزمون مسیر Forward و Legacy

اجرای اول ۲۷ PASS و ۱۴ FAIL داشت. بررسی نشان داد overlay رسمی `compose.e2e-auth-core.yml` فعال نبود: Gateway مسیرهای `/test-sso-service/` و `/test-legacy-service/` را نداشت و policy اتصال Legacy در BFF فقط mock قدیمی را مجاز می‌دانست.

پس از فعال‌سازی overlay، اجرای دوم هر ۴۱ سناریو را موفق گذراند:

- ثبت Panel، انتشار Resource Manifest، sync قرارداد frontend و تعریف Profile/Target/Route/Operation؛
- کاربران دارای هر دو دسترسی، فقط SSO، فقط Legacy و بدون دسترسی؛
- مسیر ناشناخته، method غلط، غیرفعال و فعال کردن Route، تغییر مقصد و بازگردانی آن؛
- نبود توکن، توکن نامعتبر، توکن منقضی و استفاده از credential نوع اشتباه؛
- کش Legacy، نبود Secret و بازیابی پس از بازگرداندن Secret؛
- Correlation/Audit، عدم افشای credential، نشست سرور و جداسازی شبکه؛
- اجرای مرورگر برای هر چهار نوع کاربر.

شاهد ماشینی نهایی این مجموعه در `target/e2e-auth/results.json` و نسخه قابل نگهداری در پوشه evidence این گزارش قرار می‌گیرد.

## محیط و تغییرهای انجام‌شده برای تست

### نتیجه مرورگر صفحات و گردش‌های مدیریتی

اجرای پایدار کامل ۷۲ کیس داشت: **۶۲ PASS، ۷ FAIL، ۳ BLOCKED**. سپس دو مشکل runner اصلاح و فقط همان دو کیس دوباره اجرا شدند؛ هر دو PASS شدند. ترکیب آخرین نتیجه هر کیس: **۶۴ PASS، ۵ FAIL، ۳ BLOCKED**. این عدد ترکیبی است و به‌عنوان خروجی یک اجرای کامل تازه ارائه نمی‌شود.

موارد موفق شامل فرم‌های OU و Access Group و Explain، Access Studio، میکروها و Artifact/Manifest/Navigation، Target، Route، Operation، Connection و Auth Profile، نقش و ایجاد/انتساب/لغو آن، لاگ‌ها، سه صفحه مالی، فهرست و فیلتر گزارش‌ها، زبان و مسیر ناشناخته، navigation مدیریت، رد دسترسی صفحات و API برای کاربر بدون مجوز، چهار کاربر SSO/Legacy و رد remote entry بدون نشست هستند.

| مورد باقی‌مانده | مشاهده واقعی | تفسیر و اقدام بعدی |
|---|---|---|
| آزمایشگاه اتصال OAuth2 | `/api/proxy/oauth2-demo/ping` پاسخ 500 | نمونه قدیمی OAuth2 محیط هنوز مشکل دارد؛ با موفقیت سرویس مستقل `test-sso` اشتباه نشود. لاگ Gateway/مقصد و تنظیمات این Route بررسی شود |
| ۴ صفحه HR | هیچ پاسخ مورد انتظار `/api/proxy/hr/...` در مرورگر ثبت نشد | مسیر Artifact فعال HR باید بررسی شود. آزمون token-proxy نیز هنگام دریافت یک Remote Entry رجیستری به `192.168.1.150:3999` با `ECONNREFUSED` رسید؛ ارتباط دقیق آن با HR باید با Artifact فعال تطبیق داده شود |
| ۳ کیس native Superset | registration نسخه native موجود نیست | health، فرم و runtime نسخه Docker در مجموعه مستقل بررسی شده‌اند؛ اثبات native/mTLS خارج Docker همچنان انجام نشده است |

دو ایراد runner: فهرست پوشش فقط `human-resources` را می‌شناخت در حالی که شناسه مؤثر رجیستری `hr` بود؛ و تست منو قبل از تکمیل رندر عنوان انتخاب‌شده assertion می‌زد. اکنون `hr` هم شناخته می‌شود و runner منتظر عنوان منوی مقصد می‌ماند. تست محدود `WORKFLOW-MENU,CATALOG-COVERAGE` هر دو را تأیید کرد.

اجرای قبلی مرورگر نیز نگهداری شده ولی نتیجه نهایی نیست: وقفه اتصال BFF به Authorization باعث cascade پاسخ‌های 500 شده بود. پس از پایدارشدن سرویس‌ها، اجرای کامل بالا تکرار شد؛ همان خطاهای گذرا در نتیجه نهایی مخلوط نشده‌اند.

### نتیجه گزارش و داشبورد

runner مستقل Superset، روی دارایی‌های واقعی محیط Docker و کاربر آزمایشی `e2e.none` اجرا شد. برای هر دارایی VIEW/EDIT/MANAGE ثبت و دیده‌شدن آن در کاتالوگ کنترل می‌شود؛ در `finally` فقط grantهای ساخته‌شده همان اجرا لغو و حذف از کاتالوگ و پاسخ 403 پس از لغو کنترل می‌شود.

نتیجه نهایی این مجموعه: **۴ PASS و ۱ FAIL**.

- چرخه chart موفق: هر سه action متناظر ثبت شدند، runtime پاسخ 200 داد و پس از لغو دسترسی حذف شد.
- health محیط Operation از مسیر BFF موفق بود.
- فرم «سطوح دسترسی» داشبورد در مرورگر باز شد، grantهای فعلی بارگذاری شدند و ارسال بدون دارنده/سطح با خطای اعتبارسنجی و بدون ایجاد grant رد شد.
- داشبورد Sales با ادمین در مرورگر باز شد؛ ۶ chart container و دست‌کم ۳ درخواست موفق chart data ثبت شد. این شاهد به معنی کنترل صحت عددی همه chartها نیست.
- **چرخه dashboard ناموفق است:** با وجود ثبت سطوح و دیده‌شدن دارایی در کاتالوگ، runtime کاربر آزمایشی 403 داد. لغو و پاک‌سازی grantها انجام شد. برای تعیین منشأ نهایی باید تصمیم Aurevia و مجوزهای داخلی Superset برای همان کاربر/دارایی جدا بررسی شوند؛ این گزارش آن را PASS حساب نمی‌کند.

### آماده‌سازی

ابتدا تست‌های Node به خطای sandbox از نوع `spawn EPERM` برخورد کردند؛ با اجرای مجاز workerها تست‌ها اجرا شدند. Maven اولیه سبز بود اما integrationهای permission را skip کرده بود؛ سه کانتینر موقت با پورت‌های localhost برای PostgreSQL، Redis و OpenFGA ساخته شد و اجرای نهایی بدون skip انجام گرفت.

چهار میزبان MFE از buildهای محلی با Compose مستقل روشن شدند. Overlay رسمی E2E به محیط محلی افزوده شد. نسخه native Superset به دلیل نبود `c++` در Ubuntu WSL راه نیفتاد؛ محیط رسمی Docker با imageهای موجود راه‌اندازی و health آن از BFF با HTTP 200 تأیید شد.

یک تست قرارداد قدیمی، تنظیم شبکه را به صورت متن ثابت انتظار داشت. آن تست اصلاح شد تا پارامتری بودن تنظیم و defaultهای `DEVELOPMENT` و `host.docker.internal` را برای هر دو سرویس کنترل کند. policy برنامه تغییر نکرد.

runner صفحات اصلاح شد تا نبود فایل registration نسخه native Superset کل آزمون صفحات دیگر را متوقف نکند؛ کیس وابسته به آن با BLOCKED ثبت می‌شود. این تغییر، موفقیت مصنوعی برای Superset ایجاد نمی‌کند. یک runner مستقل نیز برای grantهای dashboard/chart در محیط موجود و دادهٔ داشبورد اضافه شد: `tools/verify-superset-assets-e2e.mjs`.

## محدودیت پوشش

در پایان، سه کانتینر موقت integration و volume موقت آن‌ها حذف شدند. میزبان‌های MFE، محیط Docker گزارش و overlay آزمایشی SSO/Legacy برای بازتولید باقی مانده‌اند. grantهای موقت آزمون گزارش و role/connectionهای موقت runner طبق cleanup همان تست لغو یا غیرفعال شدند. Artifactها و تنظیمات سفارشی نامرتبط محیط به نسخه دمو بازنویسی نشدند.

این بررسی تأیید انتشار بدون قید پروژه نیست. تست‌های load/stress طولانی، disaster recovery، همه مرورگرها و دستگاه‌ها، SSO سازمانی واقعی و تمامی ترکیب‌های فیلدها اجرا نشده‌اند. runner صفحات برای محیط دمو طراحی شده و پیش‌فرض‌های آن درباره Artifact و Superset باید با رجیستری فعلی تطبیق داده شوند.

آزمون‌های VIEW/EDIT/MANAGE در سطح مجوز به معنی آزمایش تمام امکانات طراحی گزارش یا SQL Lab نیستند. مجوزهای داخلی datasource و RLS در Superset همچنان مرز مستقلی دارند.

## بازتولید

دستورهای پایه در راهنمای مدیریت آمده‌اند. integrationهای Java را با متغیرهای `AUREVIA_TEST_*` روی دیتابیس آزمایشی قابل پاک‌سازی اجرا کنید و پس از Maven حتماً `npm run test:permission:verify` را بزنید.

runnerهای تغییردهندهٔ رجیستری یا مجوز را پشت سر هم اجرا کنید. به‌خصوص آزمون‌های auth، token-proxy و grant دارایی نباید همزمان روی همان کاربر/رجیستری اجرا شوند. زمان startup یا restart سرویس را با شکست منطقی مجوز اشتباه نگیرید و اجرای پایدار را جدا ذخیره کنید.

```powershell
npm run e2e:auth:verify
node tools/verify-all-pages.mjs
node tools/verify-superset-assets-e2e.mjs
npm run swagger:verify
```

لاگ‌های محلی این بررسی در `.tmp/full-audit/` نگهداری شده‌اند. فقط گزارش‌های پالایش‌شدهٔ بدون credential برای evidence انتخاب می‌شوند؛ لاگ کامل سرویس، فایل env و اطلاعات نشست نباید وارد Git شوند.
